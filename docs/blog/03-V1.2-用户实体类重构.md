# V1.2 User 实体类：账号从字符串建模为对象

> 软件构造综合实践 · 第 3 轮迭代
> 标签 `v1.2` · 2026-11-13

V1.1 的存储是 `HashMap<String, String>`，一个用户名对一串密码。这轮要加角色和注册时间，这种扁平结构立刻不够用了——`Map` 的 key 只能放一个用户名，value 只能放一个密码，再塞第三个信息就得换数据结构。于是引入 `User` 实体，存储改为 `List<User>`。

## 一、User 里的四个字段

```java
private String username;
private String password;
private String role;          // admin / student
private String registerTime;  // yyyy-MM-dd HH:mm:ss
```

四个字段都是 `String`，包括注册时间。用 `LocalDateTime` 更"面向对象"，但下一轮 V1.3 要把用户写进 `user.txt` 再读回来，字符串可以直接按分隔符拼接和解析，日期类型反而要额外处理格式和解析异常。这一轮先选字符串，等持久化稳定之后再考虑是否换成时间类型——**先选能少踩坑的表示**。

`toString()` 把四个字段全部输出，不隐藏密码：

```java
return "User{username='" + username + "', password='" + password + "', role='" + role
        + "', registerTime='" + registerTime + "'}";
```

任务书的验收标准是"信息打印正常无缺失"，如果在这里把密码打码，验收时反而说不清"缺失"是设计还是缺陷。真实系统当然要遮，但这一轮的目的是证明对象字段完整搬过来了。

## 二、为什么要无参构造

全参构造是注册时用的，无参构造看起来没用——反正代码里从来不 `new User()`。但它是留给两类场景的：

1. 框架/反射创建对象，Java 生态里是默认约定；
2. 下一轮从文件读取时，常见写法是"先建空对象，再逐个 set 字段"。

提前留着不费成本，少写一个构造以后就要改一次类定义。

## 三、登录改成对象检索

原来 `USERS.get(username)` 一次查询就拿到密码；现在要在集合里找：

```java
private static User findUser(String username) {
    for (User user : USERS) {
        if (user.getUsername().equals(username)) {
            return user;
        }
    }
    return null;
}
```

线性遍历是 O(n)，比不上 `HashMap`。这是个明确的退步，我保留它有两个理由：用户规模在本课程里最多几十个，性能不构成问题；而 `List` 的顺序就是写入顺序，下一轮落盘时文件内容和内存顺序天然一致，读回来也不会乱。等到 V3.x 做三层架构、用户量成为需要考虑的因素时，再换索引结构。

角色判断也跟着变干净了。V1.1 里是这样：

```java
String role = "admin".equals(username) ? "ADMIN" : "STUDENT";
```

V1.2 直接读字段：

```java
String roleLabel = "admin".equals(user.getRole()) ? "ADMIN" : "STUDENT";
```

虽然还是三元表达式，但判断依据从"用户名长什么样"变成"数据里存的角色是什么"，加第三种角色时只需要改注册时赋的值。

## 四、注册流程与验收

注册时组装完整对象：

```java
User user = new User(username, password, "student", now());
USERS.add(user);
```

`now()` 统一用 `DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss")` 格式化，避免每个调用点各写一遍格式串。

实测输出：

```
注册成功，账号 zhangsan 已创建。
注册信息：User{username='zhangsan', password='123456', role='student', registerTime='2026-11-13 15:06:14'}
```

登录后：

```
登录成功！欢迎您，zhangsan。
当前身份：STUDENT
注册时间：2026-11-13 15:06:15
用户信息：User{username='zhangsan', password='123456', role='student', registerTime='2026-11-13 15:06:15'}
```

四个字段齐了，角色来自对象而不是推断，管理员账号登录时 `role='admin'` 也正确。

## 五、踩的坑：多文件编译漏文件

V1.1 只有一个类，`run.bat` 里写一条 `javac ... src\campus\SystemMain.java` 就够了。这轮多出 `entity\User.java`，如果照抄原来的命令只编译主类，会直接报错：

```
src\campus\SystemMain.java:3: 错误: 程序包 campus.entity 不存在
src\campus\SystemMain.java:25: 错误: 找不到符号
```

原因：`javac` 默认从当前目录（`-sourcepath` 的默认值）去找依赖的源文件，而 `User.java` 在 `src\campus\entity\` 下，不在它的搜索范围内。解决方式有两种：编译时把所有源文件列全，或者加 `-sourcepath src` 让 `javac` 自己去找。我选了第一种，`run.bat` 里明确列出两个文件：

```
javac -encoding UTF-8 -d out src\campus\SystemMain.java src\campus\entity\User.java
```

这样虽然啰嗦，但每次新增类都要显式加一行，反而不会出现"忘了编译某个类却以为成功了"的情况——后面 V1.3、V1.4 的类会更多，这个做法还能撑住。

## 六、单元测试

本轮补 5 条用例，集中在实体的对象契约，不涉及业务规则：

| 用例 | 验证内容 |
|---|---|
| 全参构造 | 四个字段按参数顺序写入 |
| 无参构造 | 不预置任何字段，供后续反射场景使用 |
| setter 独立生效 | 修改密码不影响账号、角色与注册时间 |
| 角色可变更 | `setRole` 可将学生改为管理员 |
| `toString` | 输出包含账号、角色与注册时间 |

实体层的测试价值在于固定字段语义。后续轮次为 `User` 增加 `equals`、`hashCode` 与角色常量时，这 5 条用例可保证既有行为不被改动。
