## 一、本轮要解决什么问题

这门课的整体要求是"20 个任务、每个任务一个独立项目、每次都基于上一版增量修改"，第一个任务看似最简单，其实要定下三件后面 19 次迭代都绕不开的事：

1. **项目骨架长什么样**——目录怎么分、包名怎么起。第一个版本定错了，后面每次迭代都要跟着改，成本会滚雪球。
2. **程序入口归谁**——所有交互都从 `SystemMain.main()` 进，这个入口后面要一直留着。
3. **角色这个概念从哪来**——系统里天然有管理员和学生两类人，权限完全不同。V1.0 虽然只做登录，但"登录完能区分出是谁"这件事必须一次做对，否则 V2.0 做资源管理时角色判定就没有落点。

至于"分几个包、抽几个工具类"——任务书明确要求**本阶段不这么做**，全部写在主类里。所以本轮的目标不是写出漂亮的代码，而是写出一段**结构正确、但明确留有技术债**的代码，让 V1.1 起的每一次迭代都有真实的改造动因可以写进博客。

## 三、关键设计与实现

### 1. 账号校验与角色判定放在一起

```java
String adminUsername = "admin";
String adminPassword = "123456";
String studentUsername = "student";
String studentPassword = "123456";

if (username.equals(adminUsername) && password.equals(adminPassword)) {
    System.out.println("登录成功！欢迎您，管理员 " + username + "。");
    System.out.println("当前身份：ADMIN");
    loggedIn = true;
} else if (username.equals(studentUsername) && password.equals(studentPassword)) {
    ...
    loggedIn = true;
} else {
    System.out.println("登录失败：账号或密码错误，请重新输入。");
}
```

这里有两处是**刻意**写成这样的：

- 账号密码是四个局部变量，不是集合也不是文件。想加一个同学，必须改代码重新编译——这正是 V1.1「动态注册 + HashMap」要解决的问题。
- 校验、提示、状态修改三件事挤在同一个 `if` 里。V1.1 会把校验拆成独立方法，V1.4 会改成抛自定义异常，V2.0 会按角色分发菜单。一次改一件事，博客就有得写。

`loggedIn` 这个布尔量承担的是"登录成功后是否退出主循环"的职责，比直接 `break` 更利于下一版在登录后接着挂业务菜单。

### 2. 全程使用 `nextLine() + trim()`，不用 `nextInt()`

```java
String choice = scanner.nextLine().trim();
```

控制台里同时混用 `nextInt()` 和 `nextLine()` 是经典坑：`nextInt()` 只吃掉数字，把回车留在缓冲区，紧接着的 `nextLine()` 会立刻读到空串。V1.0 干脆所有输入都按字符串读、再比较，代价是选项要写 `"1".equals(choice)`，收益是整个交互里不可能出现"输入被吞掉"的诡异现象。

## 四、踩过的坑

| 现象 | 原因 | 解决 |
|---|---|---|
| `javac: 找不到目录: out` | `-d out` 指定的输出目录不存在，`javac` 不会自己创建 | 先 `mkdir out`，或直接写进 `run.bat` 里先建目录 |
| 控制台中文全是乱码 | 源文件是 UTF-8，但 `javac` 默认按 GBK 读源码，编译出来的字符串本身就是错的 | 编译加 `-encoding UTF-8`，运行加 `-Dfile.encoding=UTF-8`，`run.bat` 里再加 `chcp 65001` |
| `git` 提交时提示 `LF will be replaced by CRLF` | Windows 的 `core.autocrlf=true` 会把仓库里的 LF 转成工作区的 CRLF | 无需处理，只是提醒；`.git` 里存的仍是 LF，跨平台不影响 |
| 输入选项后程序像卡住 | 其实是在等下一行的账号输入，只是提示串被上一条输出挤在同一行里（`请输入选项：账号：`） | 交互上不影响，记录在此，V1.2 改造菜单时会统一加换行 |

## 五、验收自测

| 用例 | 输入 | 预期 | 实际 | 结果 |
|---|---|---|---|---|
| 管理员登录 | `1` → `admin` → `123456` | 欢迎管理员，身份 ADMIN | 一致，输出四项权限说明 | ✅ |
| 学生登录 | `1` → `student` → `123456` | 欢迎学生，身份 STUDENT | 一致，权限为查询/预约 | ✅ |
| 登录失败 | `1` → `admin` → `111111` | 提示账号或密码错误 | 提示正确，并回到菜单 | ✅ |
| 空值校验 | `1` → 空回车 → 空回车 | 提示账号和密码不能为空 | 提示正确 | ✅ |
| 无效选项 | `9` | 提示无效选项 | 提示"请输入 1 或 0" | ✅ |

> 五组用例均为命令行实测，退出码全部为 0。

## 六、设计原则 / 模式落地

如实记录：**本任务基本没有落地设计原则**，这是任务书的要求，也是故意的。

| 原则 | 本任务状态 | 后续由哪一版接手 |
|---|---|---|
| 单一职责 | 未落地，校验/提示/输出混在主流程 | V1.1 拆出 `checkUsername()` / `checkPassword()` |
| 封装 | 未落地，用户信息还是四个字符串变量 | V1.2 建 `User` 实体，字段私有 |
| 开闭原则 | 未落地，加一种角色要改 `if-else` | V1.4 自定义异常 + 后续策略化 |

把"没有做到"写清楚，比在博客里强行凑原则名称更可信。
