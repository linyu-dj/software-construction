# V2.0 校园资源模块：系统长出业务

> 软件构造综合实践 · 第 6 轮迭代
> 标签 `v2.0` · 2026-11-13

前五轮做的都是"人"：注册、登录、落盘、报错。这一轮开始出现第一种真实的业务对象——校园资源。管理员维护资源，学生看能约的那些。

这一步的意义在于，系统第一次有了"角色看到的世界不一样"这回事。

## 一、资源实体与三态枚举

```java
public class CampusResource {
    private String id;
    private String name;
    private String type;
    private ResourceStatus status;
    private String location;
    private String description;
}
```

任务书写的是 `status` 取值 `AVAILABLE` / `OCCUPIED` / `DISABLED`。这三个值是一个封闭集合，我用了枚举：

```java
public enum ResourceStatus {
    AVAILABLE("可预约"), OCCUPIED("占用"), DISABLED("停用");
}
```

用枚举的理由不是"显得规范"，是有具体好处：

- 写错值编译期就报，不用等到运行时读到一行脏数据才发现
- 落盘时用 `name()`，存储格式和枚举名绑定，改名会被编译器提醒
- 显示时用 `toString()` 的中文标签，界面文案不用再写一遍映射

`parse()` 遇到不认识的字符串返回 `null`，由读取方决定跳过还是报错——文件可能被手工编辑坏，解析器不该替它猜一个默认状态。

## 二、编号不复用

`nextId()` 取现有最大序号加一：

```java
public String nextId() {
    int max = 0;
    for (CampusResource resource : resources) {
        int seq = parseSequence(resource.getId());
        if (seq > max) max = seq;
    }
    return ID_PREFIX + String.format("%03d", max + 1);
}
```

看起来"找最小空号"更省编号，但那样会出现一个编号先后属于两个不同资源的情况。以后预约记录按 `resourceId` 关联资源，一旦编号被复用，历史预约就会指到新资源上，排查起来非常难受。宁可留空号。

这段遍历放在 `ResourceStore` 而不是 `ResourceManager`，因为编号的合法性依赖集合的当前状态——数据在谁手里，谁负责生成。

## 三、权限做了两道门

第一道在菜单上：学生登录后看到的是

```
[1] 查询可预约资源    [0] 退出
```

没有"新增 / 修改 / 删除"这几个选项。但只在菜单上拦是不够的——菜单只是视图，任何人改一行代码就能调进去。所以第二道门放在业务方法里：

```java
public CampusResource create(User operator, String name, String type, String location, String description) {
    Validator.requireAdmin(operator, "新增校园资源");
    ...
}
```

`requireAdmin` 判断 `Roles.ADMIN.equals(operator.getRole())`，不满足就抛 `PermissionDeniedException`。这样即便绕过界面直接调方法，权限规则仍然生效。

新加的 `PermissionDeniedException` 继承 `BusinessException`，入口的 `catch` 一行没动。这是从 V1.4 那套异常体系里直接拿到的便利：加错误类型只需要加子类。

## 四、学生看不到停用和占用的详情

`listFor` 对学生返回的是过滤后的列表。`findById` 这里有个取舍：

```java
if (!isAdmin(operator) && resource.getStatus() != ResourceStatus.AVAILABLE) {
    throw new ResourceNotFoundException("未找到编号为 " + id + " 的可预约资源。");
}
```

按理说学生查一个占用资源，更准确的说法是"无权查看"。但那样等于告诉学生"这个编号存在，只是你看不到"，资源存在性就泄露了。所以按"找不到可预约资源"回应，语义上把两个信息合成一个。

这属于产品判断，不是技术判断。任务书只写了"不能查看停用 / 占用资源详情"，两种实现都合规，我选了信息更少的那种。

## 五、坏行跳过，但状态值不猜

`resource.txt` 是六个字段：

```
id|name|type|status|location|description
```

解析时三种情况跳过该行：字段不足六个、空行、状态值不认识。

前两种在 V1.3 的 `user.txt` 里已经这么处理了。第三种是这一轮新加的判断：状态只有三个合法值，读到 `BROKEN` 这种值说明文件被改坏了，这时猜一个 `AVAILABLE` 反而危险——一条本该停用的资源会重新出现在学生列表里。跳过它，让管理员看到数量不对，比悄悄放行更安全。

## 六、验收

十一组场景，重点在权限边界和数据同步：

```
首启          写入 2 个账号 + 3 个示例资源
管理员全量查询  R001~R003 三条
修改 R002     状态改为占用，resource.txt 同步
学生查询       只剩 R001、R003（占用资源不出现在列表里）
新增 R004     默认状态可预约
重启          已从 resource.txt 加载 4 个资源
删除 R004     文件同步为 3 条
删除 R999     操作未完成：未找到编号为 R999 的资源。
状态输入 4    操作未完成：状态序号只能是 1、2 或 3。
名称留空       操作未完成：资源名称不能为空。
```

全部退出码 0，堆栈扫描零命中。

有一条没法在控制台里验证：学生直接调 `create` / `update` / `delete` 会不会被拦住。菜单上根本没有入口，所以这条只能通过直接调 `ResourceManager` 来测。等单元测试补上之后会覆盖它，这里先记着。

## 七、留给下一轮的问题

这一轮 `delete` 里有一个方法：

```java
private boolean hasBookingRecord(String resourceId) {
    return false;
}
```

任务书要求"已有预约记录的资源禁止删除"，但现在还没有预约模块。我没有删掉这个校验，而是留成钩子返回 `false`，到任务 9 再换成真实查询。留钩子的好处是校验的位置和调用点都已经定好，接的时候只改一个方法体，不用回头改调用链。

下一轮 V2.1 要把所有业务方法的返回值统一成 `Result<T>`，那时候 `create` 现在这种"返回对象 + 抛异常"的写法会被改掉。
