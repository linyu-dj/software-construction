# V2.0 校园资源模块：实体建模、职责分配与权限分层

> 软件构造综合实践 · 第 6 轮迭代
> 标签 `v2.0` · 2026-11-13

前五轮的对象是"人"：账号的注册、登录、持久化与异常处理。本轮引入第一个业务实体——校园资源。管理员维护资源清单，学生只能看到可预约的部分。系统由此第一次出现"同一份数据、不同角色看到不同视图"的结构，权限判定也从单一入口扩散到查询、修改、删除三个业务动作。

## 一、资源实体与封闭状态集合

```java
public class CampusResource {
    private String id;
    private String name;
    private String type;
    private ResourceStatus status;
    private String location;
    private String description;
}
```

任务书规定状态只有三种取值，属于封闭集合，因此使用枚举而不是字符串：

```java
public enum ResourceStatus {
    AVAILABLE("可预约"), OCCUPIED("占用"), DISABLED("停用");
}
```

这一选择带来三处具体收益，而不是形式上的"规范"：

- 非法取值在编译期即被拒绝，不必等到运行期读到脏数据才暴露；
- 落盘使用 `name()`，存储格式与枚举常量名绑定，重命名会被编译器提示；
- 显示使用 `toString()` 返回的中文标签，界面文案无需另建映射表。

`parse()` 遇到不认识的字符串返回 `null`，由读取方决定跳过还是报错。文件可能被人工编辑，解析器不宜替调用方猜一个默认状态。

## 二、存储职责与编号策略

编号生成放在 `ResourceStore` 而非 `ResourceManager`：

```java
public String nextId() {
    int max = 0;
    for (CampusResource resource : resources) {
        int seq = parseSequence(resource.getId());
        if (seq > max) max = seq;
    }
    return ID_PREFIX + String.format("%03d", max + 1);
}
```

依据是信息专家（Information Expert）：编号的合法性取决于集合的当前状态，集合由存储类持有，编号生成因而归它。若放在业务类，业务类就必须直接遍历存储内部的列表，集合封装随之失效。

编号取"现有最大序号加一"，不复用空号。若改为"找最小空号"，同一编号会在不同时间指向两个不同资源；后续预约记录以 `resourceId` 关联资源，编号一旦复用，历史记录就会指向新资源，属于难以排查的数据错误。留空号的代价只是编号不连续，可以接受。

## 三、权限的两道门

第一道在视图层：学生登录后的菜单只保留查询入口，不呈现新增、修改、删除。第二道在业务方法内：

```java
public CampusResource create(User operator, String name, String type, String location, String description) {
    Validator.requireAdmin(operator, "新增校园资源");
    ...
}
```

仅在菜单上限制并不充分，菜单属于视图，绕过界面直接调用业务方法即可越过。把判定放进业务层，权限规则便不再依赖某个具体入口，符合"约束应放在能保证它的最低层"这一防御式编程原则。

新增的 `PermissionDeniedException` 继承 `BusinessException`，入口层的 `catch` 无需改动；这是 V1.4 异常分层带来的直接收益——扩展错误类型只需增加子类，符合开闭原则。

## 四、可见性取舍：不泄露资源存在性

`listFor` 对学生返回过滤后的列表。`findById` 处存在一处取舍：

```java
if (!isAdmin(operator) && resource.getStatus() != ResourceStatus.AVAILABLE) {
    throw new ResourceNotFoundException("未找到编号为 " + id + " 的可预约资源。");
}
```

按语义，"无权查看"更准确；但该措辞等于确认"此编号存在，只是当前角色不可见"，资源存在性因此泄露。实现选择按"未找到可预约资源"回应，把两条信息合并为一条。任务书只要求"学生不能查看停用与占用资源的详情"，两种实现均合规，此处选择信息暴露更少的一种。

## 五、持久化的容错边界

`resource.txt` 每行六个字段：

```
id|name|type|status|location|description
```

解析时三类行被跳过：字段不足六个、空行、状态值无法识别。前两类在 V1.3 已处理，第三类是本轮新增判断。状态的合法取值只有三个，读到 `BROKEN` 说明文件已被改坏；此时若猜成 `AVAILABLE`，一条本应停用的资源会重新出现在学生列表中。跳过该行，让管理员从数量差异中发现异常，比静默放行更安全。

## 六、与课程内容的对应

| 概念 | 落点 |
|---|---|
| 信息专家（GRASP） | `ResourceStore` 持有集合并负责编号生成与查询 |
| 纯虚构（GRASP） | `Validator`、`FileUtil` 为职责分离而设，不对应领域概念 |
| 控制器（GRASP） | `ResourceManager` 编排"校验 → 改内存 → 落盘"，不承载界面逻辑 |
| 低耦合 / 高内聚 | 存储管集合、工具管 IO、业务管编排，三方互不越界 |
| 开闭原则 | 新增异常子类无需修改入口层 catch |
| 防御式编程 | 权限在业务层二次校验；脏行跳过；非法状态不猜默认值 |
| 契约式设计 | 实体只承载数据，合法性判断上移到校验层 |

## 七、验收

十一组场景，重点在权限边界与数据同步：

```
首启            写入 2 个账号 + 3 个示例资源
管理员全量查询    R001~R003 三条
修改 R002        状态改为占用，resource.txt 同步
学生查询          只剩 R001、R003（占用资源不出现在列表）
新增 R004        默认状态可预约
重启             从 resource.txt 加载 4 个资源
删除 R004        文件同步为 3 条
删除 R999        操作未完成：未找到编号为 R999 的资源。
状态输入 4       操作未完成：状态序号只能是 1、2 或 3。
名称留空          操作未完成：资源名称不能为空。
```

十一组全部退出码 0，堆栈扫描零命中。

有一项无法通过控制台验证：学生直接调用 `create` / `update` / `delete` 是否被拦截。菜单中没有入口，只能直接调用业务类验证。这一点由本轮的单元测试覆盖。

## 八、单元测试

本轮补 26 条用例，分三个测试类：

| 测试类 | 条数 | 覆盖点 |
|---|---|---|

`ResourceManagerTest` 的越权用例绕过菜单直接调用业务方法，恰好补上了控制台验收无法覆盖的那一项。

## 九、遗留问题

`delete` 中保留了一处占位实现：

```java
private boolean hasBookingRecord(String resourceId) {
    return false;
}
```

任务书要求"存在预约记录的资源禁止删除"，但预约模块尚未建立。此处没有删除该校验，而是保留为返回 `false` 的钩子，任务 9 替换为真实查询。保留钩子的意义在于校验位置与调用点已经固定，接入时只改方法体，不改调用链。

下一轮 V2.1 将所有业务方法返回值统一为 `Result<T>`，`create` 当前"返回对象 + 抛异常"的写法将被替换。
