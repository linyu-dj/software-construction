# V1.3 IO 持久化：文件存储层的引入与读写边界

> 软件构造综合实践 · 第 4 轮迭代
> 标签 `v1.3` · 2026-11-13

前三版的账号只存在于内存，进程结束即丢失。本轮引入 `user.txt` 作为存储介质，启动时加载、注册时追加，并对存储层与业务层的职责边界作出明确划分。

## 一、职责划在哪

任务书要求新建 `FileUtil` 封装文件操作。关键在于封装时不要顺手把业务判断也搬进去——比如"密码不能少于 6 位"这种规则，绝不该出现在写文件的方法里。所以 `FileUtil` 只提供四个能力：

| 方法 | 职责 |
|---|---|
| `ensureFile()` | 文件不存在就创建空文件 |
| `loadUsers()` | 读文件 → `List<User>` |
| `saveUsers(List<User>)` | 全量覆盖写入 |
| `appendUser(User)` | 追加一行 |

业务侧只调用这些方法，不接触 `FileInputStream`、`BufferedWriter`。这就是任务书说的迪米特法则：`SystemMain` 不需要知道数据到底存在流里还是存在数据库里。

后续如果要把存储换成别的介质，改 `FileUtil` 就够，`SystemMain` 一行不用动——这是这轮真正要建立的边界。

## 二、文件格式的选择

一行一个用户，字段用竖线分隔：

```
username|password|role|registerTime
zhangsan|123456|student|2026-11-13 15:08:24
```

选竖线而不是逗号，是因为用户名里出现逗号的概率远高于竖线；选纯文本而不是对象序列化，是因为它可读、可手改、出问题时能直接在记事本里看出哪一行坏了。课程作业里，可排查比省空间重要得多。

但分隔符方案有个天然弱点：字段本身包含分隔符就会把行拆错。所以注册校验里加了一条限制：

```java
if (username.contains("|")) {
    return "账号不能包含竖线符号 |。";
}
```

这条限制不是多余。如果不加，用户注册一个 `a|b` 的账号，写进文件后第二行解析就会错位——密码变成 `b`，角色变成 `123456`，数据静默损坏，而且当时不会报错。

## 三、读与写的实现细节

**读文件时逐行解析，坏行直接跳过**，不让一条脏数据把整个启动过程带崩：

```java
String[] parts = trimmed.split("\\|", -1);
if (parts.length < 4) {
    return null;   // 字段不全，跳过这一行
}
```

用 `split("\\|", -1)` 而不是 `split("\\|")`，是因为后者会丢弃行尾的空字段。虽然当前四个字段都不允许为空，但少一个参数就埋一个隐患，不如一开始就写全。

**写用两个方法，而不是一个**。初始化时用 `saveUsers` 全量覆盖，注册时用 `appendUser` 追加一行。如果统一改成全量重写，每注册一个人就要把整个文件重写一遍，用户多了之后既慢又容易在写一半时被打断导致文件残缺。追加的代价是文件永远不会自动清理脏数据，这个取舍在本课程规模下可接受。

**编码一律显式指定 UTF-8**：

```java
new InputStreamReader(new FileInputStream(file), StandardCharsets.UTF_8)
```

不指定 `charset` 的话，`InputStreamReader` 会用平台默认编码。Windows 上默认是 GBK，写进去的中文和读回来的解析会各按各的理解，出问题时表现为"文件看着正常但读出来是乱码"。显式指定一次，跨平台也不会变。

**流全部用 try-with-resources**：`BufferedReader`、`BufferedWriter` 写在 try 的括号里，无论正常结束还是抛异常都会自动 close，不用手写 finally。

## 四、启动流程改了

```java
FileUtil.ensureFile();
USERS.addAll(FileUtil.loadUsers());
if (USERS.isEmpty()) {
    initDefaultUsers();
    FileUtil.saveUsers(USERS);
}
```

判断"要不要初始化"用的是 `USERS.isEmpty()`，不是文件大小。因为文件可能存在但内容全是坏行（手工编辑出错、上次写入中断），此时加载结果是空集合；用文件大小判断会认为"有数据"，结果一个账号都没有。用加载结果判断才是真实的。

## 五、两个容易踩的点（这轮提前挡掉了）

**1. 文件路径依赖工作目录**

`user.txt` 用相对路径，落在"程序运行目录"。`run.bat` 里先 `cd /d "%~dp0"` 才启动 java，所以文件稳定落在任务文件夹。如果从别的目录 `java -cp` 启动，文件会跑到那个目录去，重启后"数据不见了"——不是持久化失效，是读写的是两个文件。

**2. 编译要列全三个源文件**

V1.2 已经踩过"只编译主类报找不到符号"的坑，这轮类数增加到三个，`run.bat` 里就必须一路列全：

```
javac -encoding UTF-8 -d out src\campus\SystemMain.java src\campus\entity\User.java src\campus\utils\FileUtil.java
```

到这里手动列清单还撑得住；等到 V3.x 类数上双，就得换 `-sourcepath src` 或者构建脚本了。

## 六、验收：四个独立进程

持久化必须跨进程验证，同一个进程内测不出问题。

| 阶段 | 操作 | 实际输出 |
|---|---|---|
| A 首次启动 | 事先删除 `user.txt`，输入 `0` 退出 | "未找到用户数据文件，已自动创建…"；"用户数据文件为空，已写入 2 个初始化账号" |
| B 注册 | 输入 `2` → `zhangsan` → `123456` | "注册成功，账号 zhangsan 已创建并保存到 user.txt" |
| C 重启登录 | 新进程输入 `1` → `zhangsan` → `123456` | "已从 user.txt 加载 3 个用户"；登录成功，注册时间 `2026-11-13 15:08:24` |
| D 重启查重 | 新进程输入 `2` → `zhangsan` → `654321` | "账号 zhangsan 已存在，请更换" |

最终文件三行，与内存集合完全一致：

```
admin|123456|admin|2026-11-13 00:00:00
student|123456|student|2026-11-13 00:00:00
zhangsan|123456|student|2026-11-13 15:08:24
```

C 和 D 是这一轮的验收核心：两个都是新进程，数据来自文件而不是内存。

## 七、单元测试

本轮补 8 条用例：`UserTest` 3 条（实体字段契约，与 V1.2 一致），`FileUtilTest` 5 条，覆盖存储层的关键行为：

| 用例 | 验证内容 |
|---|---|
| 保存后加载往返 | 写入 3 条记录，重新加载后字段逐项相等 |
| 追加不覆盖 | 已有 2 条时追加 1 条，文件最终 3 条且原记录不变 |
| 脏行跳过 | 字段数不足、空行被忽略，合法行仍被加载 |
| 文件不存在 | `loadUsers` 返回空列表，不抛异常 |
| `ensureFile` | 父目录缺失时自动创建，文件生成后存在 |

存储层的测试必须落在临时目录。`FileUtil` 的路径相对于当前工作目录，因此 `test.bat` 先 `pushd testtmp` 再启动测试进程，跑完后演示用的 `user.txt` 不受影响。

加载路径的容错（脏行跳过、文件缺失返回空列表）是这一轮最容易在后续迭代中被改坏的部分：一旦有人把"跳过"改成"抛异常"，程序将无法在文件损坏时启动。用例据此提供了回归基线。
