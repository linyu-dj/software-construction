# V1.4 自定义异常：从堆栈输出到业务化提示

> 软件构造综合实践 · 第 5 轮迭代
> 标签 `v1.4` · `v1.4.1`（工程加固） · 2026-11-13

前三版判断失败都依赖返回值。注册方法的写法如下：

```java
String error = validateUsername(username, true);
if (error != null) {
    System.out.println("注册失败：" + error);
    return;
}
```

能用，但每加一个校验点就多一段重复的 `if (error != null)`。而且调用方很容易漏判——返回值一旦被忽略，校验就形同不存在，程序继续往下跑。这一轮改成抛出异常，并约定异常只携带"给用户看的中文句子"。

## 一、为什么继承 RuntimeException

```java
public class BusinessException extends RuntimeException {
    public BusinessException(String message) {
        super(message);
    }
}
```

选非受检异常，是因为业务规则失败可能发生在任意一层——校验方法、登录流程、以后的服务层。如果继承 `Exception`，每个被调用的方法签名都要写 `throws BusinessException`，从底层一路上挂到 `main`，签名会被异常声明污染，而这些异常最终都只在入口处理一次。`RuntimeException` 不需要声明，调用链保持干净。

代价是编译器不再提醒"这里可能抛异常"，漏处理只能在运行时发现。对业务异常来说这个代价可接受：漏处理的结果是程序中断，测试阶段就能暴露。

## 二、四个子异常对应四类失败

| 异常 | 什么时候抛 |
|---|---|
| `EmptyParamException` | 账号或密码为空、账号含竖线符号 |
| `UserExistsException` | 注册时账号已被占用 |
| `UserNotFoundException` | 登录时账号查不到 |
| `WrongPasswordException` | 登录时密码不匹配 |

分成子类而不是统一抛 `BusinessException("...")`，是为了让抛出点能表达"这是哪一类失败"。入口虽然统一按父类捕获，但子类保留了未来按类型分流的可能——比如以后要给"账号已存在"单独做一个跳转提示，就不用去解析字符串了。

有一处我没拆：密码长度不足六位，直接抛父类 `BusinessException`。

```java
if (checkStrength && password.length() < MIN_PASSWORD_LENGTH) {
    throw new BusinessException("密码长度不能少于 " + MIN_PASSWORD_LENGTH + " 位。");
}
```

任务书只列了四类子异常，长度不足属于"参数不合法"，和"参数为空"不是一回事，硬塞进 `EmptyParamException` 会误导阅读代码的人。等这类规则多起来（比如格式校验、长度上限），再补一个 `PasswordInvalidException`。因为入口按父类捕获，那时候新增子类不需要改任何调用方——这是开闭原则在这里的实际体现。

## 三、校验方法从"返回错误"改成"抛错"

改动很小，影响很清楚：

```java
// V1.3：返回 String，通过时返回 null
private static String validateUsername(String username, boolean checkUnique) { ... }

// V1.4：返回 void，失败即 throw
private static void validateUsername(String username, boolean checkUnique) {
    if (username.isEmpty()) {
        throw new EmptyParamException("账号不能为空。");
    }
    if (username.contains("|")) {
        throw new EmptyParamException("账号不能包含竖线符号 |。");
    }
    if (checkUnique && findUser(username) != null) {
        throw new UserExistsException("账号 " + username + " 已存在，请更换。");
    }
}
```

注册流程里那三段 `if (error != null) { print; return; }` 全部消失，只剩两行调用：

```java
validateUsername(username, true);
validatePassword(password, true);
```

"校验失败就停下"这个语义从"调用方记得检查返回值"变成了"异常自动中断执行"，后者是语言层面保证的。

## 四、入口统一捕获

`main` 里只保留一处 `try`，包住每条菜单指令：

```java
try {
    if ("1".equals(choice)) {
        loggedIn = doLogin(scanner);
    } else if ("2".equals(choice)) {
        doRegister(scanner);
    } else {
        System.out.println("无效选项，请输入 0、1 或 2。");
    }
} catch (BusinessException e) {
    System.out.println("操作未完成：" + e.getMessage());
} catch (Exception e) {
    System.out.println("系统异常，请稍后重试。");
}
```

两层 `catch` 的目的不一样：第一层是业务失败，把异常的 `message` 原样给用户看，因为 message 就是按用户能读懂的句子写的；第二层兜住其余异常，用一句笼统提示代替堆栈。两个分支都没有 `printStackTrace()`，也没有把 `e.toString()` 拼进提示里——任务书要求的"屏蔽堆栈"就是这一条。

这里有个我自己不太满意的地方需要写出来：第二层 `catch (Exception e)` 把非业务异常的细节完全吞掉了。真实项目里这是隐患，排查线上问题必须把堆栈写进日志文件。课程作业只要求"不向用户暴露"，所以这轮先这样处理，日志能力留给以后的迭代。

登录成功的判定也跟着变了：`doLogin` 在失败路径上抛异常，成功路径才 `return true`，所以 `loggedIn` 不会被异常路径误置。

## 七、定稿后补的一轮工程加固

功能验收全部通过之后，我又把 V1.4 的代码重新读了一遍，发现几个"功能没问题、但写法站不住"的地方。这一轮不加功能，只调整代码的位置和边界，改完打 tag `v1.4.1`。

### 1. `FileUtil` 把 IO 故障当成了业务失败

原来的写法：

```java
} catch (IOException e) {
    System.out.println("读取用户数据失败：" + e.getMessage());
}
return users;
```

文件读不出来，打印一句提示，然后返回一个空列表继续往下跑。程序于是认为"这个系统里一个用户都没有"，接着重新写入两个演示账号——如果挂掉的是后面那次写入，用户数据就有丢失风险。这类问题的麻烦之处在于它不报错，只在很久以后表现为"数据莫名其妙没了"。

改成把异常抛出去，由入口统一兜底：

```java
private static RuntimeException wrap(IOException e, String action) {
    return new UncheckedIOException(action + "：" + e.getMessage(), e);
}
```

`UncheckedIOException` 是 JDK 自带的包装类，原始异常放在 `cause` 里，排查时不会丢。抛出之后，`catch (Exception e)` 打印"系统异常，请稍后重试。"，不暴露路径和堆栈，用户侧的表现反而更干净。

这条判断的依据是：**能就地处理的问题才捕获，处理不了的要让它往上传**。打印一行然后继续，既没有恢复数据，也没有让调用方知道失败，属于把问题藏起来。

### 2. 用户集合搬进 `UserStore`

`SystemMain` 原来持有 `List<User>`，还自己写了一个线性查找：

```java
private static User findUser(String username) {
    for (User user : USERS) { ... }
}
```

把集合和查询一起挪进 `UserStore`，对外只留 `add` / `findByUsername` / `exists` / `snapshot`。理由是查询逻辑依附于数据结构，集合在谁手里，查找就该归谁——这是"信息专家"的直接应用。顺带解决了一个隐患：原先 `USERS` 是静态字段，任何新增代码都能直接 `USERS.add(...)` 绕过校验，现在只能通过 `add` 进，入口收窄了。

`snapshot()` 返回 `Collections.unmodifiableList(new ArrayList<>(...))`，不把内部集合递出去。这是防御性封装：调用方拿到的副本改了也不影响存储里的数据。

### 3. 校验和角色字面量各归各处

`validateUsername` / `validatePassword` 从主类抽到 `Validator`，方法名改成 `requireValidUsername` / `requireValidPassword`。`require` 这个前缀说明"不满足就抛异常"，读代码时不用再猜返回值。

`"admin"` / `"student"` 原来散在三处：注册时写死 `"student"`、初始化账号时各写一次、展示时用 `"admin".equals(...)` 判断身份。收敛到 `Roles` 常量类之后，要改角色名只动一个文件。

同一个角色值在 `User` 里仍是 `String`，没有换成枚举。原因是 `user.txt` 第一版就按 `admin|...` 存，换成枚举要么改字段类型、要么每次 `name().toLowerCase()`，读写都变绕。等资源状态（可预约 / 占用 / 停用）那种封闭集合出现时再用枚举更合适——那三个值本来就是有限的、不可扩展的。

### 4. `User` 补上相等性

实体只有 `toString`，没有 `equals` / `hashCode`，结果就是两个用户名相同、字段相同的对象判断为不相等。现在用不上，但以后要做去重、放进 `Set`、写 `assert` 都会踩到。

按账号判等，密码不参与——同一个用户改密码后仍然是同一个人。`hashCode` 跟着只对账号取值，保持与 `equals` 一致。

### 5. 主类只剩流程

改完之后 `main` 只有三件事：

```java
try (Scanner scanner = new Scanner(System.in)) {
    try {
        initStorage();
        printBanner();
        runMenuLoop(scanner);
    } catch (Exception e) {
        System.out.println("系统异常，请稍后重试。");
    }
}
```

`Scanner` 换成 try-with-resources，因为它实现了 `AutoCloseable`，比 `finally` 里手写 `close()` 少一层嵌套。菜单选项 `"0"` / `"1"` / `"2"`、默认密码、初始化注册时间也都提成常量，逻辑里不再出现裸字面量。

### 6. 改完必须证明行为没变

重构的定义是"外部行为不变"，所以光编译通过不算数。把原来的 8 组验收重新跑了一遍，另外补了"账号含竖线"和"无效选项"两组，10 组输出与改前逐字对应，堆栈扫描仍然零命中，`user.txt` 落盘格式也没有变化：

```
admin|123456|admin|2026-11-13 00:00:00
student|123456|student|2026-11-13 00:00:00
zhangsan|123456|student|2026-11-13 17:25:46
```

唯一可见的差异是建文件那句提示从绝对路径改成了文件名 `user.txt`。这个改动是有意的：绝对路径会暴露 `C:\Users\...` 这类本机信息，换成相对文件名对用户来说信息量并没有减少。

### 7. 单元测试

本轮补 27 条用例，是本阶段测试密度最高的一轮，原因在于这一轮引入了三处可独立验证的规则来源：校验器、存储容器与异常分层。

| 测试类 | 条数 | 覆盖点 |
|---|---|---|
| `UserTest` | 5 | 按 `username` 判定的 `equals` / `hashCode`、`Roles` 常量、构造与 `toString` |
| `ValidatorTest` | 9 | 空账号、`null` 账号、含竖线账号、重复账号、登录不查重、密码长度下限、空白密码、密码含竖线、合法输入 |
| `UserStoreTest` | 8 | 新增与查找、`exists`、`size` / `isEmpty`、`replaceAll` 清空、快照只读、重复新增、加载后重建 |
| `FileUtilTest` | 5 | 保存加载往返、追加不覆盖、脏行跳过、无文件返回空、`ensureFile` 返回布尔值 |

三条用例值得单独说明：

- 用户名含竖线被拒绝。`user.txt` 以 `|` 分隔字段，若账号本身含竖线，写回后行会被解析成多段，属于存储格式对业务字段的隐性约束，必须由校验层显式拦截；
- 登录路径不查重。注册要求账号唯一，登录要求账号存在，两条规则方向相反，用同一个 `requireValidUsername` 加布尔参数区分，用例分别固定两种语义；
- 快照只读。`snapshot()` 返回副本，调用方修改副本不得影响容器内部状态，这与后续 `save` 的数据来源直接相关。

### 8. 没有做的事

这轮刻意没碰两样东西：`Result<T>` 统一返回（属于 V2.1）和 `service` / `dao` 分层（属于任务 10）。加固的边界是"把已有的代码放到该在的位置"，一旦提前把后面的架构做出来，下一轮迭代就没有可讲的东西了，也容易和任务书要求的演进顺序对不上。
