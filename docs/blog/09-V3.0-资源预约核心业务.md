# 预约业务：核心闭环打通

> 软件构造综合实践 · 第 9 轮迭代
> 标签 `v3.0` · 2026-11-13

前八轮都是各管一段：账号归账号，资源归资源。这一轮把它们接起来，做第一个真正有前后依赖的业务——学生提交预约，管理员审核，资源状态跟着变，学生还能取消。

任务书里这一节写得最细，条目也多：预约记录 8 个字段、4 种状态、时间冲突、审核联动、删除校验、条件查询，还有一条「全部返回 Result」。下面按实现的顺序记。

## 一、先定状态，再写流程

`ReserveStatus` 是这轮唯一新增的枚举：

```java
public enum ReserveStatus {
    PENDING("待审核"), PASS("已通过"), REJECT("已驳回"), CANCEL("已取消");

    public boolean isFinal() {
        return this == REJECT || this == CANCEL;
    }
}
```

`isFinal()` 是为了取消那里的一句话判断。原来要写成 `status != PENDING && status != PASS`，现在 `if (record.getStatus().isFinal())` 就够了。以后再加「已过期」这种状态，只要它属于终态，`cancel` 一个字都不用改。

资源那边的 `ResourceStatus` 已经在 V2.0 定好了，三种状态，这轮不改。

## 二、冲突判定只比「已通过」的记录

这是我觉得这一轮最需要想清楚的一处。任务书写的是「同一资源在同一时间段已有通过预约则禁止提交」，只说了通过。

```java
boolean overlaps = record.getReserveStartTime().isBefore(endTime)
        && startTime.isBefore(record.getReserveEndTime());
```

这里用的是半开区间。如果照直觉写成 `!endTime.isBefore(otherStart) && !startTime.isAfter(otherEnd)`，那 9:00–11:00 和 11:00–13:00 会被判成冲突——两段紧挨着的预约其实没有任何重叠时间。验收里专门留了一条「首尾相接不算冲突」。

为什么只算 PASS：待审核的申请还没占住资源。要是把它也纳入冲突判断，一个还没批的申请就能挡住别人的申请，管理员最后只能在两条互相冲突的待审记录里挑一条——这个限制应该由管理员在审核时承担，不该在提交时就卡死。

也正因为只算 PASS，验收里那组「时间冲突」不是顺着正常流程走出来的。资源一旦审核通过就变成占用状态，学生根本提交不了。必须先让管理员手动把资源改回可预约（现实里对应退租、维修结束），冲突校验才会被触发。这组用例走的就是这条路径。

## 三、审核要同时改两张表

```java
resource.setStatus(ResourceStatus.OCCUPIED);
record.setStatus(ReserveStatus.PASS);
FileUtil.saveReserves(reserveStore.snapshot());
FileUtil.saveResources(resourceStore.snapshot());
```

资源和预约的状态必须一起改。只改预约，重启后会出现「记录显示已通过、资源还显示可预约」，下一个学生照样能提交，然后管理员发现资源被两个人同时占着。

两个 `save` 紧挨着写，能做到「正常路径下两张表一致」，但做不到「中途崩了也一致」。这一点我在 README 里写成了已知局限，没打算在这一轮解决——没有事务的前提下，能做的只是缩小不一致的时间窗口。

驳回就简单了，只改记录：

```java
record.setStatus(ReserveStatus.REJECT);
FileUtil.saveReserves(reserveStore.snapshot());
```

资源本来就没被动过，不用恢复。

## 四、取消之后资源得回来

```java
boolean wasPass = record.getStatus() == ReserveStatus.PASS;
record.setStatus(ReserveStatus.CANCEL);
FileUtil.saveReserves(reserveStore.snapshot());
if (wasPass) {
    restoreResource(record.getResourceId());
}
```

`wasPass` 这个变量不能省。取消一条待审核的申请时，资源可能正被别人的预约占着，这时候去「恢复」会把别人的占用状态抹掉。

`restoreResource` 里还有一层判断：

```java
resourceStore.findById(resourceId).ifPresent(resource -> {
    if (resource.getStatus() == ResourceStatus.OCCUPIED) {
        resource.setStatus(ResourceStatus.AVAILABLE);
```

找不到资源就跳过。虽然 PASS 状态的资源禁止删除，但驳回之后是可以删的，删完再来取消这条已驳回记录（其实取消不了，`isFinal` 会挡住），总之不能假设资源一定还在。

## 五、把 V2.0 的假钩子换成真查询

V2.0 写删除的时候，我给 `ResourceManager` 留过一个方法：

```java
private boolean hasBookingRecord(String resourceId) {
    return false;
}
```

当时预约模块还不存在，只能留个占位，注释里写「任务 9 会替换成真实查询，不动调用点」。这轮兑现了：

```java
if (reserveStore.hasPassReservation(resource.getId())) {
    throw new BusinessException("资源 " + trimmedId
            + " 存在已通过（PASS）的预约记录，禁止删除。请先处理该预约。");
}
```

代价是 `ResourceManager` 的构造器多了一个参数，资源业务直接拿到了预约存储。这是跨业务域的依赖，按分层原则不该有。任务书下一轮就是三层架构重构，我故意留着这个耦合没绕，重构时才有具体的痛点可讲。

## 六、主类这次真的变长了

菜单从 5 项涨到 8 项（管理员）和 5 项（学生）。加完预约之后 `SystemMain` 变成 400 多行，读输入、调方法、打表格混在一起，`dispatchAdmin` 里一串 `else if`。

我知道这不是好形状。但任务 10 才要求拆 `ui` / `service` / `dao`，现在提前拆，等于把下一轮的活干完了，本轮反而说不清「为什么要分层」。所以这轮让它长，长到一眼能看出问题为止。

顺带记一个细节：表格里时间用 `yyyy-MM-dd HH:mm`，落盘用 `yyyy-MM-dd HH:mm:ss`。落盘精度高是因为 `applyTime` 是真实提交时刻，秒级差异在排查问题时有用；界面上显示到分钟就够了，再多一列秒会把表格撑得很宽。

## 七、单元测试：没有 JUnit 怎么写

老师提了单元测试的要求，课程又限定不引第三方框架，于是自己拼了一套最小的：

- `Assert`：五个断言方法，失败抛 `AssertionError`。
- `TestRunner`：`run(名称, Runnable)` 包一条用例，捕获异常记 FAIL，最后打印「通过 X 失败 Y」，有失败就 `System.exit(1)`。
- 三个测试类，分别对着 `UserManager`、`ResourceManager`、`ReserveManager`。

41 条用例，按四类分布：正常路径、边界（首尾相接、空集合、编号顺延）、越权（学生新增资源、管理员提交预约、学生审核、取消他人预约）、错误输入（时间格式、过去时间、不存在的编号）。

有两个地方花了点心思：

第一，测试不能污染正式数据。业务方法里是真的会写文件的，`appendUser`、`appendReserve` 都跑不掉。所以 `test.bat` 先 `pushd testtmp` 再启动 JVM，所有写入落在临时目录，跑完正式的三个 txt 一个字都没变。

第二，每条用例自己造 store 和 manager，不共享。共享能少写几行，但一条失败会带崩后面一串，定位反而慢。现在每条用例是一个独立的 lambda，坏哪条看名字就知道。

跑出来是这样：

```
[PASS] 提交成功生成待审核记录
[PASS] 与已通过预约重叠被拒绝
[PASS] 首尾相接不算冲突
...
通过：41    失败：0    合计：41
```

## 八、验收：24 组把闭环走一遍

按业务顺序排：首启 → 提交两条重叠的待审申请 → 管理员审核通过一条、驳回一条 → 学生看到两种状态 → 取消已驳回（被挡）→ 取消已通过（资源恢复）→ 换 R002 再走一遍 → 手动改回可预约后触发冲突 → 条件查询 → 删除被 PASS 挡住 → 取消后能删 → 重启加载 → 四种错误输入。

结果和预期一致，24 组全过。取消的三条记录都留在 `reserve.txt` 里，状态是 CANCEL：

```
B001|R001|student|2026-11-13 18:36:47|2026-11-20 09:00:00|2026-11-20 11:00:00|CANCEL|部门例会
B002|R001|student|2026-11-13 18:36:48|2026-11-20 10:00:00|2026-11-20 12:00:00|REJECT|重叠时段
B003|R002|student|2026-11-13 18:36:56|2026-11-25 14:00:00|2026-11-25 16:00:00|CANCEL|
```

没有删掉它们。预约记录能回答「这个时段有没有人申请过、批了没有」，删了就查不回来了。状态字段本身就是为了留痕而存在的。

## 九、一个批处理的坑

`run.bat` 从 V1.2 起一直是这么写的：

```
dir /s /b src\*.java > sources.txt
javac -encoding UTF-8 -d out @sources.txt
```

之前验收都是我用脚本直接调 `javac` 跑的，没走 bat。这次真的双击了一下，报「找不到文件：C:\Users\18723\Desktop\软件构�?�\Task09-...\src\campus\SystemMain.java」。

原因是 `javac` 读 `@sources.txt` 用的是系统默认编码，而 `dir` 在 `chcp 65001` 下写出来的是 UTF-8，中文目录名「软件构造」在参数文件里变成一串乱码，`javac` 解析出来的路径自然找不到。

修法是参数文件里只写相对路径：

```
src\campus\SystemMain.java
```

批处理里把 `%CD%\` 这个前缀从每行剥掉，写进参数文件的全是 ASCII。这样 `javac` 用 GBK 还是 UTF-8 读都无所谓。顺手把 Task06/07/08 的 `run.bat` 一起改了，它们有同样的毛病。
