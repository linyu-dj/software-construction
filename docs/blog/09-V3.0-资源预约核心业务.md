# V3.0 资源预约：状态联动的业务闭环与单元测试落地

> 软件构造综合实践 · 第 9 轮迭代
> 标签 `v3.0` · 2026-11-13

前八轮各自独立：账号归属用户模块，资源归属资源模块。本轮把两者串联，形成第一个存在前后依赖的业务——学生提交预约，管理员审核，资源状态随审核结果变化，学生可取消已提交的预约。任务书对此节要求最细：预约记录八个字段、四种状态、时间冲突判定、审核联动、删除校验、条件查询，并要求全部返回 `Result`。

## 一、状态建模与终态判断

`ReserveStatus` 是本轮新增的枚举：

```java
public enum ReserveStatus {
    PENDING("待审核"), PASS("已通过"), REJECT("已驳回"), CANCEL("已取消");

    public boolean isFinal() {
        return this == REJECT || this == CANCEL;
    }
}
```

`isFinal()` 用于取消操作的入口判断。若按原写法需要判断 `status != PENDING && status != PASS`；改为 `if (record.getStatus().isFinal())` 后，状态集合与"是否为终态"的对应关系收敛到枚举内部，业务代码不再持有该知识。以后新增"已过期"等终态，只需在枚举中声明，`cancel` 逻辑无需改动。

资源侧的 `ResourceStatus` 已在 V2.0 定义，本轮不改动。

## 二、时间冲突判定

任务书要求"同一资源在同一时间段已有通过预约则禁止提交"，判定对象仅限已通过记录。

```java
boolean overlaps = record.getReserveStartTime().isBefore(endTime)
        && startTime.isBefore(record.getReserveEndTime());
```

采用半开区间语义。若按直觉写成 `!endTime.isBefore(otherStart) && !startTime.isAfter(otherEnd)`，则 9:00–11:00 与 11:00–13:00 会被判为冲突，而两段首尾相接的预约并不存在重叠时间。验收用例中专门保留了"首尾相接不算冲突"一条。

仅比较 `PASS` 记录的理由：待审核申请尚未占用资源。若将其纳入冲突判断，一条尚未批准的申请即可阻止他人提交，管理员最终只能在两条互相冲突的待审记录中选择一条。该限制应由管理员在审核阶段承担，不宜在提交阶段提前施加。

也正因如此，验收中的"时间冲突"用例无法沿正常流程触发：资源一旦审核通过即变为占用状态，学生无法再次提交。必须由管理员先将资源改回可预约（现实中对应退租或维修结束），冲突校验才会被触发。

## 三、审核操作的原子性边界

```java
resource.setStatus(ResourceStatus.OCCUPIED);
record.setStatus(ReserveStatus.PASS);
FileUtil.saveReserves(reserveStore.snapshot());
FileUtil.saveResources(resourceStore.snapshot());
```

资源与预约的状态必须同时修改。若只改预约，重启后将出现"记录显示已通过、资源仍显示可预约"，下一个学生仍可提交，进而造成同一资源被两条通过记录占用。

两次 `save` 相邻执行，可以保证"正常路径下两张表一致"，但无法保证"中途失败仍一致"。在没有事务机制的前提下，能够做到的只是缩短不一致窗口。该限制已写入 README 的已知局限，本轮不处理。

驳回操作只修改记录：

```java
record.setStatus(ReserveStatus.REJECT);
FileUtil.saveReserves(reserveStore.snapshot());
```

资源状态未变动，无需恢复。

## 四、取消与资源释放

```java
boolean wasPass = record.getStatus() == ReserveStatus.PASS;
record.setStatus(ReserveStatus.CANCEL);
FileUtil.saveReserves(reserveStore.snapshot());
if (wasPass) {
    restoreResource(record.getResourceId());
}
```

`wasPass` 不可省略。取消一条待审核申请时，资源可能正被其他通过记录占用；若不加判断直接"恢复"，会将他人的占用状态抹除。

`restoreResource` 内部仍有第二层判断：

```java
resourceStore.findById(resourceId).ifPresent(resource -> {
    if (resource.getStatus() == ResourceStatus.OCCUPIED) {
        resource.setStatus(ResourceStatus.AVAILABLE);
```

找不到资源则跳过。虽然通过状态的资源禁止删除，但驳回后可以删除，因此不能假定资源必然存在。这是防御式编程中的"不假设外部状态"：前置条件无法由本方法保证时，方法自身仍需处理异常情况。

## 五、删除校验：从占位钩子到真实查询

V2.0 中曾保留一处占位：

```java
private boolean hasBookingRecord(String resourceId) {
    return false;
}
```

当时的注释写明"任务 9 替换为真实查询，不改调用点"。本轮兑现：

```java
if (reserveStore.hasPassReservation(resource.getId())) {
    throw new BusinessException("资源 " + trimmedId
            + " 存在已通过（PASS）的预约记录，禁止删除。请先处理该预约。");
}
```

代价是 `ResourceManager` 的构造器增加一个参数，资源业务直接持有预约存储。这是跨业务域的依赖，按分层原则不应存在。任务书下一轮即三层架构重构，此处刻意保留该耦合，使重构时有具体问题可分析，而非抽象讨论"分层的好处"。

## 六、界面层的增长与分层缺口

菜单由 5 项增至 8 项（管理员）与 5 项（学生）。加入预约功能后，`SystemMain` 增长至 400 余行，输入读取、业务调用、表格打印混在同一类中，管理员分发逻辑变成一串 `else if`。

这一形态不符合高内聚低耦合的要求，但本轮不拆分。任务 10 才要求分离 `ui` / `service` / `dao`，此时提前拆分等于提前完成下一轮工作，反而无法说明"为何需要分层"。本轮保留该问题，使其在代码中可见。

另有一处细节：表格显示时间用 `yyyy-MM-dd HH:mm`，落盘用 `yyyy-MM-dd HH:mm:ss`。落盘精度更高是因为 `applyTime` 为真实提交时刻，秒级差异在排查问题时有效；界面显示到分钟即可，多一列秒会使表格过宽。两种格式分别封装在 `TimeUtil` 的 `format` 与 `formatShort` 中，避免格式串散落在各处。

## 七、单元测试设计

课程要求补充单元测试，且限定不引入第三方依赖，因此自行实现最小测试框架：

- `Assert`：`isTrue` / `isFalse` / `equals` / `contains` / `notNull` / `fail`，失败抛 `AssertionError`；
- `TestRunner`：以 `run(名称, Runnable)` 包裹单条用例，捕获异常记 `FAIL`，汇总后按失败数设置进程退出码，便于批处理判断结果；
- 三个测试类，分别对应 `UserManager`、`ResourceManager`、`ReserveManager`。

41 条用例按四类分布：

| 类型 | 示例 |
|---|---|
| 正常路径 | 提交成功生成待审核记录；审核通过后资源转为占用 |
| 边界条件 | 首尾相接不算冲突；空集合编号从 B001 开始；编号不复用空号 |
| 越权操作 | 学生新增资源；管理员提交预约；学生审核；取消他人预约 |
| 错误输入 | 时间格式非法；起始时间早于当前；编号不存在 |

两处设计决定：

第一，测试不得污染演示数据。业务方法中确实会写文件，`appendUser`、`appendReserve` 均如此。因此 `test.bat` 先 `pushd testtmp` 再启动 JVM，所有写入落在临时目录，跑完正式的三个数据文件不受影响。

第二，每条用例自行构造 `store` 与 manager，不共享状态。共享可少写几行，但一条失败会连带后续用例，定位成本更高。当前每条用例是独立 lambda，失败时按名称即可定位。

执行结果：

```
[PASS] 提交成功生成待审核记录
[PASS] 与已通过预约重叠被拒绝
[PASS] 首尾相接不算冲突
...
通过：41    失败：0    合计：41
```

## 八、验收

二十四组场景按业务顺序排列：首启 → 提交两条重叠的待审申请 → 管理员通过一条、驳回一条 → 学生查看两种状态 → 取消已驳回（被拒）→ 取消已通过（资源恢复）→ 换 R002 重复上述流程 → 手动改回可预约后触发冲突 → 条件查询 → 删除被 `PASS` 记录拒绝 → 取消后可删除 → 重启加载 → 四类错误输入。

结果与预期一致，二十四组全部通过。取消后的记录保留在 `reserve.txt` 中，状态为 `CANCEL`：

```
B001|R001|student|2026-11-13 18:36:47|2026-11-20 09:00:00|2026-11-20 11:00:00|CANCEL|部门例会
B002|R001|student|2026-11-13 18:36:48|2026-11-20 10:00:00|2026-11-20 12:00:00|REJECT|重叠时段
B003|R002|student|2026-11-13 18:36:56|2026-11-25 14:00:00|2026-11-25 16:00:00|CANCEL|
```

记录未被删除。预约记录的价值在于回答"某时段是否有人申请、是否获批"，删除即不可查。状态字段本身即为留痕而存在。

## 九、工程问题：javac 参数文件的编码

`run.bat` 自 V1.2 起采用如下写法：

```
dir /s /b src\*.java > sources.txt
javac -encoding UTF-8 -d out @sources.txt
```

此前验收均由脚本直接调用 `javac`，未经过批处理文件。本轮实际执行时报错：

```
找不到文件：C:\Users\18723\Desktop\软件构�?�\Task09-...\src\campus\SystemMain.java
```

根因是 `javac` 读取 `@sources.txt` 时使用系统默认编码，而 `dir` 在 `chcp 65001` 下写出的是 UTF-8；中文目录名"软件构造"在参数文件中被错误解码，解析出的路径自然不存在。

修复方式是参数文件只写相对路径：

```
src\campus\SystemMain.java
```

批处理中先用 `set "PREFIX=%CD%\` 取得前缀，再以延迟展开逐行剥离，写入参数文件的全部为 ASCII 字符。这样 `javac` 无论按 GBK 还是 UTF-8 读取均不受影响。Task06/07/08 的 `run.bat` 存在同一问题，一并修复。

这类问题的教训是：路径中包含非 ASCII 字符时，任何"由程序读取文件再解析"的环节都要确认编码约定，不能假定两端一致。

## 十、与课程内容的对应

| 概念 | 落点 |
|---|---|
| 状态建模 | 四种预约状态用枚举表达，终态判断收敛到 `isFinal()` |
| 不变量与契约 | 冲突判定只比较 `PASS` 记录；取消仅在原状态为 `PASS` 时释放资源 |
| 防御式编程 | `restoreResource` 不假设资源存在；非法时间行整行跳过 |
| 异常分层 | 时间冲突、状态非法、记录不存在各自定义异常，均继承 `BusinessException` |
| 单一职责 | `ReserveManager` 只做编排，时间解析交给 `TimeUtil`，IO 交给 `FileUtil` |
| 信息专家（GRASP） | 预约查询、编号生成、`hasPassReservation` 均置于 `ReserveStore` |
| 已知耦合 | `ResourceManager` 依赖 `ReserveStore`，留待任务 10 分层时消除 |
| 测试隔离 | 用例在临时目录执行，业务写文件不影响演示数据 |
