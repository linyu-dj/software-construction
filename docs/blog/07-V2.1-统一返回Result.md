# V2.1 统一返回值：Result 契约与业务异常的职责划分

> 软件构造综合实践 · 第 7 轮迭代
> 标签 `v2.1` · 2026-11-13

V2.0 结束时，业务方法的返回约定已经不一致：

```java
CampusResource create(...)         // 返回对象，失败抛异常
boolean addResource(...)           // 返回布尔值，失败原因不可知
CampusResource findById(String id) // 找不到返回 null
```

三种约定并存，调用方每调用一个方法都要先确认它属于哪一种。这是《软件构造》中典型的"不一致的返回约定"坏味道：接口没有统一语义，错误处理成本被迫转移到每个调用点。本轮将返回值统一为 `Result<T>`。

## 一、统一前后的对比

V2.0 判断"资源是否查到"的写法：

```java
CampusResource resource = store.findById(id);
if (resource == null) {
    throw new ResourceNotFoundException(...);
}
```

查询列表返回 `List`，空列表与"查询失败"在类型上无法区分；新增返回对象、失败抛异常；修改与删除返回 `void`、失败同样抛异常。调用方需要三套判断逻辑。

统一后四种情况共用一个形状：

```java
Result<CampusResource> result = manager.create(...);
if (result.isSuccess()) { ... } else { System.out.println(result.getMsg()); }
```

`boolean` 无法携带失败原因，`null` 无法携带失败原因，`Result` 两者都可携带。

## 二、Result 的设计约束

```java
public class Result<T> {
    private boolean success;
    private String msg;
    private T data;

    public static <T> Result<T> success(T data) { ... }
    public static <T> Result<T> success(String msg) { ... }
    public static <T> Result<T> success(String msg, T data) { ... }
    public static <T> Result<T> fail(String msg) { ... }
}
```

三条约束值得记录：

- 构造器私有，只能经静态工厂创建，避免出现 `new Result(true, null, null)` 这种"成功但无内容"的对象；
- `fail` 强制将 `data` 置空，失败仍携带数据时调用方极易取错值；
- 类内不含业务判断、不读写文件、不打印。它只承担"封装结果"一件事，符合单一职责；打印属于视图层职责。

## 三、异常与 Result 的分工

任务书要求两套机制配合使用。实现分工是：校验层继续抛异常，业务方法内部转换为 `Result`。

```java
public Result<User> login(String username, String password) {
    try {
        Validator.requireValidUsername(store, username, false);
        Validator.requireValidPassword(password, false);

        User user = store.findByUsername(username);
        if (user == null) {
            throw new UserNotFoundException("账号 " + username + " 尚未注册，请先注册。");
        }
        if (!user.getPassword().equals(password)) {
            throw new WrongPasswordException("密码错误，请重新输入。");
        }
        return Result.success("登录成功，欢迎您 " + username + "。", user);
    } catch (BusinessException e) {
        return Result.fail(e.getMessage());
    }
}
```

校验为什么不改为返回 `Result`：校验的语义是"不满足即中止"，异常能保证调用方无法忽略；若返回 `Result`，每个调用点都要补一层 `if (!result.isSuccess()) return result;`，反而失去异常的价值。

由此形成两类失败的分界：

- 业务规则失败（账号重复、密码错误、权限不足）——继承 `BusinessException`，在业务方法内转换为 `Result.fail`；
- 系统故障（IO 异常）——不以业务失败处理，仍向上抛出，由入口统一提示。

这与《软件构造》的异常策略一致：可预期的规则失败走业务异常，不可预期的环境故障向上传递，两者不混用同一个出口。

## 四、调用方视角的变化

改造前，主类需要认识五种异常并分别 `catch`；改造后只有一条判断：

```java
Result<User> result = USER_MANAGER.login(username, password);
if (!result.isSuccess()) {
    System.out.println("操作未完成：" + result.getMsg());
    return null;
}
```

界面层只依赖 `Result` 这一最小接口，不需要知道背后存在多少种异常类型。新增一种业务失败，界面层无需改动——这既是迪米特法则的应用，也是接口分离原则的体现：视图依赖抽象的结果契约，而非具体异常集合。

## 五、用户业务的搬迁

注册与登录原在主类中，本轮迁入 `UserManager`。直接原因是任务书要求用户模块的注册、登录、查询统一返回 `Result`，而返回 `Result` 需要有方法承载；方法放在入口类不符合职责划分。

搬迁后主类职责收敛为三步：读输入、调业务、打印结果。业务规则不再出现在界面代码中。`UserManager` 承担的是 GRASP 中控制器（Controller）的角色：接收界面请求，协调校验、存储与持久化，自身不实现界面细节。

## 六、行为等价性验证

返回值改变，行为不得改变。V2.0 的十一组场景原样重跑：

```
首启            2 个账号 + 3 个示例资源
管理员查询       3 条
修改 R002        改为占用并落盘
学生查询         只剩 2 条可预约
新增 R004        默认可预约
重启             加载 4 条
删除 R004        同步为 3 条
删除 R999        操作未完成：未找到编号为 R999 的资源。
状态序号 4       操作未完成：状态序号只能是 1、2 或 3。
名称留空         操作未完成：资源名称不能为空。
```

全部通过，堆栈零命中。唯一差异是成功提示中增加"资源"二字，属措辞调整。

## 七、单元测试暴露的一处重载缺陷

本轮补 25 条用例，其中一条在首次运行时失败：

```
[FAIL] 成功并携带数据，提示为默认文案
  -> AssertionError: 期望：操作成功，实际：payload
```

原因是 `Result` 同时声明了 `success(T)` 与 `success(String)`。当实参为字符串且类型参数推断为 `String` 时，两个重载都可接受，编译器按"更具体的重载优先"选中 `success(String)`，字符串因此被当作提示而非数据。

现有调用方没有依赖这条路径，所以运行期未暴露。测试将此行为固定下来：

```java
Result<String> result = Result.success("payload");
Assert.equals("payload", result.getMsg(), "字符串实参被解析为提示");
Assert.isTrue(result.getData() == null, "字符串实参不会进入 data");
```

修复方向有两个：去掉 `success(String)`，改用 `successWithMsg(String)`，使两个工厂方法名称可区分；或保留现状并在类注释中写明限制。本轮选择后者，因为改动会波及全部调用点，而任务 10 的分层重构本就要重写这些调用。

这条用例的价值不在断言本身，而在于把"重载解析的真实行为"写进回归集：以后有人调整工厂方法，测试会立刻报出差异。

其余用例分三类：`ResultTest`（6 条，覆盖四个工厂方法与 `toString`）、`UserManagerTest`（9 条，覆盖注册、登录、查询的成功与失败路径）、`ResourceManagerTest`（10 条，覆盖越权、编号、空参数、删除）。

## 八、与课程内容的对应

| 概念 | 落点 |
|---|---|
| 单一职责 | `Result` 只封装结果，不做判断、不打印、不碰 IO |
| 值对象 | 私有构造 + 静态工厂，实例创建后字段不再变化 |
| 接口分离 | 视图只依赖 `isSuccess` / `getMsg` / `getData` 三个访问方法 |
| 迪米特法则 | 界面不与具体异常类型耦合 |
| 异常策略 | 业务失败转 `Result`，系统故障继续上抛 |
| 契约式设计 | 校验方法以 `require` 前缀声明前置条件，不满足即抛异常 |
| 测试作为规格 | 重载解析行为由用例固定，避免后续修改悄悄改变语义 |

## 九、遗留的重复代码

每个业务方法都有一段相同的 `try/catch (BusinessException)`，六个方法即六段。本轮未处理。

任务书明确要求"本阶段不做分包分层，代码结构维持现状，为任务 10 三层重构保留痛点"。此时若先把异常收敛到统一入口，等于提前完成分层，后续迭代将失去可讨论的问题。这是有意的技术债，而非遗漏。
