# V2.1 统一返回 Result：让调用方只判断一件事

> 软件构造综合实践 · 第 7 轮迭代
> 标签 `v2.1` · 2026-11-13

上一轮结束时，业务方法的返回值已经很难记了：

```java
CampusResource create(...)        // 返回对象，失败怎么办？抛异常
boolean addResource(...)          // 返回 boolean，为什么失败？自己猜
CampusResource findById(String id) // 找不到返回 null
```

三种约定混在一起，调用方每调一个方法都要回去翻它是哪种风格。这一轮把返回值统一成 `Result<T>`。

## 一、先看代码，就知道原来的问题

V2.0 里判断"资源查到了没有"，写法是这样的：

```java
CampusResource resource = store.findById(id);
if (resource == null) {
    throw new ResourceNotFoundException(...);
}
```

而查列表返回的是 `List`，空列表和"查询失败"看起来一样；新增返回对象，失败抛异常；修改和删除返回 `void`，失败也抛异常。调用方要写三种不同的判断。

统一之后，四种情况都变成一个形状：

```java
Result<CampusResource> result = manager.create(...);
if (result.isSuccess()) { ... } else { System.out.println(result.getMsg()); }
```

`boolean` 没法携带"为什么失败"，`null` 没法携带"失败原因"，`Result` 两样都能带。

## 二、Result 只做三件事

```java
public class Result<T> {
    private boolean success;
    private String msg;
    private T data;

    public static <T> Result<T> success(T data) { ... }
    public static <T> Result<T> success(String msg) { ... }
    public static <T> Result<T> success(String msg, T data) { ... }
    public static <T> Result<T> fail(String msg) { ... }
}
```

构造器私有，只能走静态工厂。这样就不会出现 `new Result(true, null, null)` 这种"成功但不知道成功在哪"的对象。

`fail` 一定把 `data` 置空——失败还带数据，调用方很容易拿错东西。

类里没有一行业务判断，也不打印任何东西。打印是视图层的事，`Result` 只负责"把结果装好"。

## 三、异常没有退休，只是换了岗

任务书说异常和 Result 两套机制配合使用，我的做法是：**校验层继续抛异常，业务方法内部转成 Result**。

```java
public Result<User> login(String username, String password) {
    try {
        Validator.requireValidUsername(store, username, false);
        Validator.requireValidPassword(password, false);

        User user = store.findByUsername(username);
        if (user == null) {
            throw new UserNotFoundException("账号 " + username + " 尚未注册，请先注册。");
        }
        if (!user.getPassword().equals(password)) {
            throw new WrongPasswordException("密码错误，请重新输入。");
        }
        return Result.success("登录成功，欢迎您 " + username + "。", user);
    } catch (BusinessException e) {
        return Result.fail(e.getMessage());
    }
}
```

为什么不把校验也改成返回 Result？因为校验是"不满足就停下"的语义，异常能保证调用方不会忘记判断；如果校验返回 Result，每个调用点又要多一层 `if (!result.isSuccess()) return result;`，反而把异常的好处丢了。

界面层看到的是 Result，业务内部仍然是异常，两边各拿各的方便。

## 四、控制台的变化

改造前，主类要认识五种异常：

```java
catch (UserNotFoundException e) { ... }
catch (WrongPasswordException e) { ... }
catch (ResourceNotFoundException e) { ... }
```

现在只有一条：

```java
Result<User> result = USER_MANAGER.login(username, password);
if (!result.isSuccess()) {
    System.out.println("操作未完成：" + result.getMsg());
    return null;
}
```

登录、注册、增删改查全部走这一个判断。以后再加一种业务失败，界面层不用改——这是迪米特法则在起作用：界面只依赖 `Result` 这个"最小接口"，不需要知道背后有多少种异常。

## 五、这一步也顺手搬了用户业务

注册和登录原本在主类里，这一轮搬进了 `UserManager`。理由不是"为了分层"，而是任务书要求"用户模块的注册、登录、查询统一返回 Result"——要返回 Result 就得有方法，方法放在主类里不太对。

搬完之后主类的职责变得很清楚：读输入、调业务、打印结果。业务规则一条都不在界面里。

## 六、行为必须一模一样

返回值改了，行为不能改。把上一轮的 11 组场景原样重跑：

```
首启          2 个账号 + 3 个示例资源
管理员查询     3 条
修改 R002     改为占用并落盘
学生查询       只剩 2 条可预约
新增 R004     默认可预约
重启          加载 4 条
删除 R004     同步为 3 条
删除 R999     操作未完成：未找到编号为 R999 的资源。
状态序号 4     操作未完成：状态序号只能是 1、2 或 3。
名称留空       操作未完成：资源名称不能为空。
```

全部通过，堆栈零命中。唯一的文案差异是成功提示里多了"资源"两个字，属于措辞调整。

## 七、这轮留下的重复代码

每个业务方法里都有一段一样的 `try/catch (BusinessException)`，六个方法就是六段。看着不舒服，但这一轮没有动它。

任务书明确写了"本阶段不做分包分层，代码结构维持现状，为任务 10 三层重构保留痛点"。现在就把异常收敛到一个统一入口，等于提前做分层，后面那一轮就没有可讲的东西了。这属于有意的技术债，不是忘了改。
